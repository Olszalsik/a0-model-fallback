sync Model Fallback System — user manual
Agent Zero normally calls one model at a time. If that model is rate-limited, times out, or errors, the run stops. The Model Fallback System turns that single call into a resilient rotation through your fallback candidates, then layers optional "keep-alive" fixes on top so the agent loop and the WebUI stay healthy under load. This page explains, in plain English, what each piece does, when you'd use it, and when (if ever) to turn it off.

1. What this plugin is (and isn't)

What it is: a self-contained resilience layer for model calls. When your primary model fails, it automatically tries the next one in your fallback list, manages cooldowns so a rate-limited model isn't hammered, and keeps the surrounding plumbing (the utility call, the memory recall task, langchain imports) from freezing the agent.

What it isn't: it does not choose your models or edit your model config. It works with whatever FALLBACK chain you already configured in Agent Zero. If you have no fallback models configured, the cascade has nothing to rotate to — the resilience features (timeout guard, shim) still work, but the rotation part is a no-op.

Self-contained: no official Agent Zero file is modified. Everything is installed through Agent Zero's extension hooks. Disabling the plugin (or toggling a feature off) restores stock behavior.

2. How to use it

Open the plugin's settings panel (Settings → Plugins → Model Fallback System → gear icon). You'll see three groups:

  • Timeouts — how long to wait for a single model response before moving on. Per request, not per whole cascade.
  • Fallback Cycles — how many full passes through your fallback list to attempt before giving up, and the pause between passes.
  • Resilience features — independent on/off switches for the optional fixes (see §5). The menu_book book icon reopens this page.

Make your changes and hit Save. Most timeout / cycle changes take effect on the next agent turn. The resilience toggles take effect on the next server start (the install hooks run at boot), except the context-size guard which re-reads its config every turn.

The clamped value is what gets saved, so the runtime never sees an out-of-range setting. (v2.6.5 fixed a bug where the box displayed the clamp but saved the raw typed value.)

3. The model cascade

When a model call fails, the cascade tries the next fallback instead of giving up. It classifies each error:

  • Rate limit (429) — the model goes on cooldown using the server's Retry-After header (or a tuned default when there is no header). The cascade skips it until the cooldown expires, then retries it.
  • Auth failure (401/403), credit depletion (402), model not found (404), context overflow — marked permanently broken for the session and skipped on every later cycle. These won't fix themselves by retrying.
  • Invalid JSON — rotates to the next model (a different parser path is tried).
  • Timeout / transient 5xx — retried with the next model after a brief delay. The utility-model timeout guard (§5) sets the hard cap.

If every candidate is permanently broken, the cascade stops early instead of pointlessly cycling (the early_exit_on_all_permanent knob). If every candidate is only rate-limited (will recover), it enters extended-retry mode: paced retry loops timed for real-world reset windows (minutes to hours), so a 5-hour Ollama limit or a daily credit reset doesn't hard-stop your run.

The cooldown store is in-memory and shared across agents in the same process, so one agent's rate-limit doesn't silently re-fire on another. A cross-agent "healthy label" signal (§4) lets a peer's success clear a stale cooldown sooner.

4. The adaptive cascade (v2.6)

Five refinements, all wired into both the chat and utility cascades:

  1. Warm / cold per-call timeouts. The first call to a label (within cascade_warm_window_s, default 10 min) gets the full cold timeout. Subsequent calls within the window get the short warm ceiling (cascade_warm_timeout_s, default 20s). Cloud providers return warm calls in 1–5s; a flat 300s timeout on a warm call wastes minutes per candidate when several are hung. A user-set TIMEOUT= kwarg still wins.
  2. Per-provider capacity inference. The cascade classifies each label so "busy" isn't treated as "broken":
    • concurrent-paid (local ollama/*) — a 429 is a competing agent, so no cooldown is written and primary-skip escalation is skipped.
    • router (omniroute/*) — a self-healing gateway that re-routes the next call. A 429 skips cooldown entirely; a 5xx gets a tiny router_cooldown_s (default 5s). Router labels are exempt from primary-skip escalation.
    • unlimited-paid (a0_venice/*) — normal cooldown handling.
    • free-per-minute (everything else, incl. OpenRouter free models) — a 429 is a real free-tier limit; normal cooldown.
  3. Stagnation backoff. When cycle_stagnation_threshold consecutive full cycles complete with zero successes (every model still in cooldown), the cycle sleep is multiplied by cycle_stagnation_factor to give quota-exhausted upstreams time to recover. One log line per outage, not per cycle.
  4. No preempt of healthy calls. A CancelledError (you stopped the run) is split from a TimeoutError so an externally-cancelled but otherwise-healthy call is not punished with a cooldown.
  5. Cross-agent healthy-label reset. When any agent succeeds on a label, that label is marked healthy for health_horizon_s (default 60s). Other agents' cooldowns for the same label become eligible to be cleared (only cleared, never overwritten) on their next cycle — so one agent's rate-limit doesn't lock out a peer that needs the same endpoint right now.

v2.6.3: router-class labels (omniroute/*) are exempt from the 20s warm fast-path and always use the cold ceiling — a self-healing gateway routing free/slow upstream tiers is not a fast warm cloud call, and the 20s warm ceiling was timing out the OmniRoute utility model in the "free coding fast" presets.

v2.6.4: when a warm call does time out, the warm label is evicted so the retry uses the cold ceiling instead of looping at the short warm timeout. Label-agnostic (covers omniroute/* too); this is what actually closes the 20s warm-loop lag.

5. Resilience features (the toggles)

Three independent pieces, each targeting a specific failure mode. They share no state and can be toggled on/off independently. The defaults are conservative; turn a piece on only if you see the symptom it fixes (most are already on by default).

5.1 Utility-model timeout guard v2.2

Symptom: a hung utility call (typically a slow ollama model on CPU) blocks the agent loop indefinitely. The cascade's per-request timeout eventually fires, but the WebUI has already frozen.

What it does: wraps Agent.call_utility_model in asyncio.wait_for(...) with a hard cap (max_wait_s, default 180s). On timeout it best-effort closes the inner litellm coroutine and raises a RepairableException("utility_model_timeout") so the LLM is told the utility failed and can rephrase or skip.

Default: ON.

5.2 Context-size guard v2.3

Symptom: when the conversation grows past the utility model's context window, every utility candidate returns ContextOverflow. The cascade can't recover in a single cycle because the history is already too long.

What it does: at message_loop_prompts_after, if the total chars in loop_data.history_output exceed max_chars (default 50000), the oldest messages are dropped until the budget is met, with a one-liner notice so the LLM knows early turns were trimmed.

Default: OFF. Trimming can confuse the LLM (it loses the early conversation), so this is opt-in. Enable only when you see cascading ContextOverflow across all utility candidates in a single cycle.

5.3 LangChain v0 → v1 import shim v2.4

Symptom: ModuleNotFoundError: No module named 'langchain.prompts' on langchain-v1-only Docker images. Agent Zero's helpers/call_llm.py uses the v0 import path; langchain v1 moved it to langchain_core.prompts.

What it does: at process start / agent init, registers langchain_core.prompts under the legacy langchain.prompts path (and langchain_core.messages under langchain.schema) via sys.modules. A no-op on langchain v0.x installs (the real module is left alone).

Default: ON.

Removed: event-loop housekeeping loop v2.2 REMOVED in v2.5

A standalone while True housekeeping loop (coroutine sweep + WebSocket keepalive pulse + stats tick) shipped in v2.2 and was removed in v2.5 — it was a never-tested same-day fix whose only real symptom was a per-minute housekeeping loop not alive, respawning log line. The housekeeping_enabled and second_pulse_path_enabled keys are still accepted on save for back-compat but are no-ops at runtime.

6. The toggle switches & why they matter

Each feature has a top-level boolean on context.settings. The switch you see is the real value that gets saved — toggling and saving persists it to config.json for the current scope (global / project / agent profile).

Setting keyDefaultEffect when OFF
utility_timeout_guard_enabled true Utility call falls back to the cascade's per-request timeout. Hung calls can freeze the loop longer.
context_size_guard_enabled false History is not trimmed. ContextOverflow spirals must be fixed by other means (a smaller model, shorter conversation).
langchain_compat_enabled true Shim is not installed. v0-style imports fail with ModuleNotFoundError on v1-only images.
housekeeping_enabled / second_pulse_path_enabled REMOVED false Accepted on save for back-compat but no-ops at runtime (the underlying loop was deleted in v2.5).

v2.6.5 fixed a bug where the toggle switches did not save: the panel previously bound each switch with both x-model and :checked, an Alpine anti-pattern where the one-way :checked fought the two-way x-model, so a click never committed and every switch reopened OFF. Switches now use x-model only and missing keys are backfilled to their effective default on open, so a default-ON feature displays ON even when the loaded config predates the toggle.

7. WebUI cache: where it moved (v2.6.6)

The server-side WebUI extensions cache (the 2s TTL cache + non-lossy circuit breaker on get_webui_extensions) used to live in this plugin as the webui_extensions_cache_enabled toggle. In v2.6.6 it was migrated to the ui_loader_optimizer plugin (v3.5.0), which already owned the complementary client-side fetch coalescing. The two layers now live in one plugin and compose multiplicatively — the client never sends duplicate calls, the server never re-walks the filesystem for the calls that do arrive. Configure it there under Settings → Developer → UI load optimizer → Server-side extension cache.

If you develop a plugin and need zero-delay feedback on file saves, temporarily turn off that server-side cache (the 2s TTL can hide edits for up to 2s); the client coalescing can stay on.

8. When to disable a feature

Utility-model timeout guard

  • You see RepairableException("utility_model_timeout") on a model that is actually producing slow-but-correct output. Raise max_wait_s first; disable only if that isn't enough.

Context-size guard

  • The LLM forgets early instructions after a trim. The notice injection helps but is not a substitute for an actually-fitting context; the right fix is usually a larger model window or a shorter conversation.

LangChain shim

  • You're on langchain v0.x and want to remove the indirection. The shim is a no-op when the v0 module is already in sys.modules, so this is rarely necessary.

9. Migration (upstream adds the equivalent)

If a future Agent Zero release ships its own equivalent of one of these features, the recommended migration is:

  1. Toggle OFF the matching feature in this plugin.
  2. Restart the server.
  3. Confirm the upstream equivalent is active (e.g. a new keepalive ping in the server logs).
  4. If the migration is permanent, the corresponding helper file can be deleted:
    • helpers/utility_timeout.py
    • helpers/langchain_compat.py
    • the context-size-guard extension (extensions/python/message_loop_prompts_after/_10_context_size_guard.py)

Full per-version design notes and migration guidance live in AGENTS.md.

10. Observability — the stats endpoint

Read-only counters are exposed at GET /api/plugins/model_fallback/stats:

{
  "version": "2.6.6",
  "utility_timeout": {
    "calls_total": 89,
    "timeouts_total": 3,
    "max_observed_wait_s": 67.2
  },
  "context_size_guard": {
    "trims": 0,
    "messages_dropped": 0
  },
  "langchain_compat": {
    "installed": true,
    "shims": {
      "langchain.prompts": true,
      "langchain.schema": false
    }
  }
}

The endpoint inherits the framework's requires_auth=True — the WebUI's logged-in session passes that transparently. It is read-only; no POST/PUT.
